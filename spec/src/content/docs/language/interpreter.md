title: Interpreter (Evaluator)
description: How the code is interpreted at runtime.

The Caja language currently utilizes a **Tree-Walking Interpreter** to execute code. This is the final phase of the compilation pipeline, where the Abstract Syntax Tree (AST) generated by the parser is actually run to produce results.

Unlike compilers which translate the AST into machine code or bytecode, a tree-walking interpreter evaluates the AST directly in memory.

## Implementation Details (`/internal/pipeline/evaluator`)
The interpreter logic resides entirely within the Go `internal/pipeline/evaluator` package. 

### The `Eval` Function
The beating heart of the interpreter is the `Eval(node, env)` function located in `evaluator.go`. It is a deeply recursive function that takes an AST Node and the current runtime Environment.

It uses a Go `switch` statement to determine the concrete type of the node and routes it to the appropriate sub-function:
- **Literals** (`NumberLiteral`, `StringLiteral`): Immediately return their raw Go value wrapped in an object.
- **Variables** (`Identifier`): The evaluator looks up the variable's string name inside the `Environment` memory map and returns its stored value. If it's missing, it throws a runtime error.
- **Assignments** (`LetStatement`, `AssignStatement`): The evaluator recursively calls `Eval` on the right-hand expression to calculate the result, and then stores that result in the `Environment` under the variable's name.
- **Math/Logic** (`InfixExpression`): Evaluates the left side, evaluates the right side, and then performs the underlying Go operation (e.g., `+`, `-`, `==`) on the two resulting objects.

### Closures and Functions
When the evaluator encounters a `FunctionLiteral` (a function definition), it doesn't execute the function body. Instead, it creates a **Closure**. It bundles the function's AST node alongside a pointer to the current `Environment`.

Later, when that function is invoked (`CallExpression`), the evaluator creates a brand new inner Environment (so local variables don't leak out), points its "outer" reference to the closure's saved environment, and then evaluates the function's block statement. This is how Caja natively supports functional closures and lexical scoping.

## The Runtime Environment
To track state during execution, the evaluator passes around an `Environment` object (defined in `/internal/pipeline/environment`). 

The `Environment` is essentially a wrapper around a Go hash map (`map[string]Object`). It acts as the RAM for your scripts, storing variable names as keys and the evaluated data objects as values. Because environments can have an "outer" reference, the interpreter can easily simulate deeply nested scopes (like variables inside an `if` block inside a `fn`).
