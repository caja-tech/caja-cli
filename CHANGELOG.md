# Changelog

All notable changes to the Caja Language and CLI will be documented in this file.

## [Unreleased]

### Added
- **`@caja/js`: JavaScript as Caja data** — a new package that builds an expression/statement tree and renders it to source, exactly the way `@caja/ui` builds a `View` tree and renders it to HTML. `@caja/ui`'s `onX` handlers and `scriptBlock` now take a `[JsStmt]` rather than a string, so the JavaScript a page ships is **correct by construction**: expressions and statements are separate types (a statement cannot land where an expression belongs), `jsStr` escapes quotes, backslashes, newlines and `</`, identifiers are checked against a plain-identifier alphabet, and every composite expression renders parenthesised so operator precedence is never consulted and never wrong. The capability this adds over `js.raw` is the one a literal cannot reach: a script that depends on values the build computed — a page list, a label, a generated lookup table — with the data escaped on the way in. Surface: literals, arrays, objects, member/index access, calls, `new`, arrows, 14 binary and 3 unary operators, ternaries; `const`/`let`/assignment/expression statements, `if`/`if-else`, `return`, function declarations, `for…of`; plus DOM shorthands (`jsGetElementById`, `jsSetText`, `jsToggleClass`, ...) that are ordinary composition of the rest. `jsRaw`/`jsRawStmt` accept a `js.Script` and are the single door for arbitrary syntax — a door that validates, and one that cannot be forged, since a `String` does not narrow to a `Script` even in a hand-built struct literal. The scaffolded static-page site's "Interactivity" section now builds its handler this way, sharing two Caja string constants between the page text and the script.
- **JavaScript in a static page, validated at compile time** — a new `js` builtin module whose one function, `js.raw(code)`, returns an opaque `Script`. `@caja/ui` gained an `onX` handler per event (`onClick`, `onInput`, ... ~90, mirroring the `onX` set) plus `scriptBlock(code)` for page-level JavaScript, and these are the only things that emit a `Script` — so every script a Caja program can put in a page has necessarily been parsed by a real JavaScript parser (esbuild, in-process) before the build succeeded. A missing bracket is now a Caja build error pointing at the `js.raw` call instead of a page that loads and silently does nothing. This closes a real gap: `renderToString` drops Caja event handlers (a static page has no Caja runtime to attach them to), so before this the entire event surface was unusable in the project type most people scaffold. Three consequences worth knowing: the argument must be a string **literal** (that is what puts the source in front of the validator while the compiler is still running — a script assembled at runtime could not be checked, so it is rejected rather than silently trusted); a `Script` widens to `String` but a `String` never narrows to a `Script`, the same one-directional rule enums use, which is what forces everything through the validator; and `js.raw` rejects `</script` in any casing, even inside a comment, because inside a raw-text element that ends the element then and there and entity-escaping cannot rescue it. The scaffolded static-page site gained a working "Interactivity" section demonstrating it.
- **@caja/ui: tags are typed** — `view(tag: HTMLElement)` replaces `el(tag: String)`, validated against a new closed `HTMLElement` enum covering the HTML Living Standard element set (~115 members, obsolete elements deliberately omitted). `view("div")` and `view(HTMLElement.Dvi)` are both compile-time errors now, where `el("dvi")` used to render markup that silently did nothing. `customView(tag: String)` is the unchecked escape hatch for a web component, an SVG/MathML child, or anything else outside the enum — the enum is the typed front door, not a wall. Enum members never collide with same-named declarations (`HTMLElement.Style` alongside the `Style` type, `HTMLElement.Option` alongside `option()`): members live in the enum's own namespace.
- **@caja/ui: the full event-handler surface** — a closed `DOMEvent` enum, one generic `on(target, event, handler)`, and a named one-line wrapper per member (~90: mouse, pointer, touch, keyboard, form and input, focus, clipboard, drag-and-drop, scroll, loading, disclosure/dialog, media, animation, transition, slots). Exactly the relationship the modifier chain has to `CSSProperty`, one layer over: `onClick(btn) => {...}` and `on(btn, DOMEvent.Click) => {...}` are the same call. Previously only `onClick`/`onInput` existed, so a `View` could hold a `Handler` for any event but nothing could put one there. Window/document-scoped events (`beforeunload`, `DOMContentLoaded`, `popstate`, `visibilitychange`) are excluded on purpose — `on()` attaches to an element, so they could never fire.
- **@caja/ui: `@keyframes` in Caja** — `Keyframe`/`Keyframes` with `keyframe(offset, template)`, `keyframes(name, frames)`, `keyframesCss` and `keyframesStylesheet`. This is the one CSS shape that isn't "a selector plus declarations" — an `@keyframes` block nests a whole list of declaration blocks — so it gets its own type rather than reusing the flat `Rule`. A frame's `offset` (`"0%"`, `"from"`) is raw text for the same reason a selector is; the declarations inside each frame go through the ordinary modifier chain, so `CSSProperty` still checks them. Two `CSSProperty` members were added to support the conversions below: `Transform` and `Content` (whose modifier is named `pseudoContent`, since CSS `content` only means anything on a pseudo-element and `content` is this library's most common parameter name).
- **`caja init` installs dependencies for any project type that declares them** — the install step is now gated on whether the rendered scaffold actually contains a `package.json` (`scaffoldHasPackageJSON`), not on a hardcoded `projectType == TypeHTTPAPI` check that had to be kept in agreement with the template trees by hand. Both remaining project types gain a `package.json.tmpl`: static-page declares `@caja/siriguela` and `@caja/ui`, and web-app declares those two plus `@caja/dom`. Every one is a direct dependency because every one is a direct import — npm resolving `@caja/ui` transitively through the theme would not describe what these projects actually use. Adding npm dependencies to a project type is now purely a template change, with no Go edit at all. Note that neither UI package is published yet, so the install currently fails with a warning rather than succeeding — `installDependencies` has always degraded that way, and the scaffolded README still documents the manual `node_modules/@caja/` layout.
- **Enum Types**: Added a closed `enum` type to the language (e.g. `enum CSSProperty { Padding = "padding", Margin = "margin" }`). The backing primitive type is inferred from the members' literal values, and an enum value widens implicitly to that backing type (e.g. into a `String` parameter or a `map[String]String` slot) — but a bare value of the backing type does not narrow to the enum, so a typo'd or unrelated string is a real compile-time type error at the call site, not a runtime one. Enums have no distinct Go type of their own at compile time — a member access transpiles directly to its literal value.
- **Zero-parameter trailing lambdas**: extended the existing Kotlin-style trailing-lambda sugar (`call(args) paramName => { ... }`) to also accept a zero-parameter form: `call(args) => { ... }` (or `call(args) => expr`), with no identifier before the `=>`, appends a zero-arg `fn() -> T { ... }` as the call's last argument. Lets an event-handler-shaped last parameter (e.g. `fn() -> Nothing`) use the same sugar as a one-parameter callback — `onClick() => { ... }` instead of `onClick(fn() -> Nothing { ... })`. Pure parser-level desugaring into the already-existing `ast.FunctionLiteral` shape, same as the one-parameter form — no lexer, `ast`, analyzer, or compiler changes needed.
- **static-page projects are multi-page sites**: `caja init --type static-page` now scaffolds a `pages/` folder (one `.caja` module per page, each exporting `page`), an `assets/` folder (with a sample SVG), and a `main.caja` that is a short site builder — it lists the pages, wraps each in a shared layout with navigation, and writes them all. `caja build`/`caja serve` copy `assets/` into `dist/assets/` (recreated from scratch each build) after running the generator, through one shared `generateStaticPage` path so the two commands can't drift. `caja init` now creates nested template directories, which it silently could not before (any subdirectory template failed with "no such file or directory").
- **siriguela: pages and navigation** — `Page` (`title`, `path`, `content`), `definePage`, `navLinks(pages, currentPath)` (marks the current link with `aria-current='page'`) and `htmlDocument(title, stylesheetHref, body)` (a complete document as a String, doctype included). The library still never writes a file: that stays in the project's `main.caja`, so importing siriguela never makes a program un-runnable with `caja run`.
- **siriguela: CSS classes defined in Caja** — `Class`, `styles()`, `class(name, template)`, `variant(cls, pseudo, template)` for `:hover`-style rules, `withClass`/`withClasses` to apply them, and `classCss`/`classStylesheet` to emit them. A class is built by the same modifier chain that styles a View, so `CSSProperty` validation applies and nothing is duplicated.
- **LSP: folding ranges for `#region`/`#endregion`** — the language server answers `textDocument/foldingRange`, giving the VS Code extension (and any other LSP client) collapsible C#-style regions: `#region [name]` ... `#endregion`, name optional, nesting supported. These are ordinary `#` comments to the rest of the pipeline — no new lexer/parser/analyzer/compiler syntax — so folding is computed by a small raw-text scan (`internal/lsp/folding.go`) that tracks string/date-literal spans and requires the `#` to start its line, rather than from the AST.
- **siriguela: arbitrary CSS rules and media queries** — `Rule` (`rule(selector, template)`, `rulesCss`, `rulesStylesheet`) covers element selectors, comma-grouped selectors, descendant/child/sibling combinators and attribute selectors — anything `Class` can't express because the selector isn't a fixed set of properties. Only a `Rule`'s declarations go through the modifier chain and `CSSProperty`; its selector is plain, unchecked text, the same as a selector in a CSS-in-JS template literal. `MediaQuery` (`media(query, rules)`, `mediaCss`) groups Rules under one `@media` condition. `stylesheet(rules, classes, queries)` renders and joins all three (rules, then classes, then media queries — cascade order) into one String. Ten `CSSProperty` members were added to support it: `Background`, `PaddingTop`/`PaddingBottom`, `MarginTop`, `BorderTop`/`BorderBottom`/`BorderCollapse`, `OverflowX`, `VerticalAlign`, `PointerEvents`, each with a matching modifier. The static-page scaffold's `main.caja` now builds its entire `dist/style.css` — previously six hand-written CSS strings — from `Rule`/`MediaQuery`/`Class` lists via one `stylesheet()` call.
- **siriguela: `code`/`codeBlock`, `className`/`elementId`** — inline and block code (samples are HTML-escaped and keep their newlines), and the two attribute-modifiers that hook a View up to a stylesheet rule or an anchor target.
- **static-page scaffold: `definePage` calls use named arguments** — `ui.definePage(title: "...", path: "...", content: content)` instead of three positional arguments, taking advantage of `develop`'s new named-call-argument support (merged into this branch). `title`/`path` are two adjacent strings with nothing at the call site to tell them apart positionally; naming them makes a swapped-argument typo a compile-time error at the call site instead of a silently wrong page.
- **static-page scaffold and siriguela's own docs adopt wildcard imports** — all three template files (`main.caja.tmpl`, `pages/index.caja.tmpl`, `pages/about.caja.tmpl`) switch from `import "@caja/siriguela" as ui` to `import * from "@caja/siriguela" as ui`, dropping the `ui.` prefix throughout their real code and, in the reference page, its own documentation samples too — the compose-style DSL siriguela was meant to read as. The `ui` alias stays bound as a fallback. Verified zero name collisions against `array`/`string`/`map`/`doc`'s exports across siriguela's ~190 exported names, and that generated output (`dist/*.html`, `dist/style.css`) is unchanged apart from the documentation text itself. `siriguela/README.md` documents wildcard import as an alternative to the existing qualified/named forms, including the trade-off that a wildcard-imported name is silently shadowed by (or silently shadows) a same-named local declaration, unlike a named import's hard "already declared" error.

### Changed
- **Breaking: `@caja/ui`'s JavaScript handlers lose the `Script` suffix** — `onClickScript` is now `onClick`, `onInputScript` is `onInput`, and so on for all 90. The two handler families across `@caja/ui` and `@caja/dom` now share one set of names, so the event reads the same everywhere and which *kind* of handler you get is decided by which package you reached into rather than by a suffix. The overlap is safe because Caja raises a real ambiguity error, not a silent pick, when a bare name is wildcard-imported from two packages: `ambiguous reference to 'onClick': wildcard-imported from 'ui' and 'dom'. Suggestion: qualify it (ui.onClick or dom.onClick)`. The scaffolds use the shape that error recommends — wildcard-import `@caja/ui`, qualify `@caja/dom` — and the web-app template now shows `onClick([...])` and `dom.onClick(fn)` side by side on two buttons.
- **Breaking: the Caja-function event handlers moved from `@caja/ui` to `@caja/dom`** — the ~90 `onClick`/`onInput`/`onKeyDown` functions that take a `fn() -> Nothing` now live in `@caja/dom` (so: `dom.onClick(...)`), next to the `mount()` that attaches them. The split is by what makes a handler work rather than by category: calling a Caja function from a browser event needs a Caja runtime in the browser, which only a wasm `web-app` build ships, whereas `@caja/ui`'s ~90 `onX` functions emit JavaScript as an inline event attribute and therefore work in every target. `@caja/ui` is down to one handler family and 279 exports; `@caja/dom` is up to 96. Each package keeps its own private event enum, since sharing one would mean exporting a type neither public API accepts — at the cost of two lists that must be kept in step.
- **`mount()` now applies JavaScript handlers too** — `attachHandlers` previously read only `.handler`, so an `onClick` written for a static page was *silently ignored* in a web-app build. It now sets the corresponding inline attribute, exactly as `renderToString` does, so the same component code behaves the same way in both targets. Caja handlers still go through `browser.on` as before.
- **Breaking: `@caja/ui`'s generic `on()` and the `DOMEvent` enum are private** — the ~90 named handler functions (`onClick`, `onInput`, ...) were always the intended surface, and `on()` existed only as the one place they funnel through. With `on()` private there is no exported function that accepts a `DOMEvent`, so exporting the enum would advertise a type a consumer has nowhere to pass; both are now internal. The named function *is* the event — it is not a runtime choice, so nothing was gained by making it a value you could pass around.
- **`<script>`, `<style>`, `<textarea>` and `<title>` are rendered as the raw-text elements they are** — `renderToString` used to run `escapeHTML` over every element's text, which for these four is not merely unnecessary but wrong: a browser never decodes entities inside them, so an escaped `<` arrived as the literal `&lt;` and whatever the content was meant to be was silently broken. This is what makes a `<script>` body possible at all, and it also lifts a long-standing restriction — every CSS-emitting function in `@caja/ui` was written to avoid `>` entirely, because a child combinator in a `<style>` came out as `&gt;` and the rule silently never matched. Selectors are unrestricted now. Keyed off the tag rather than a flag on `View`, so there is no way to build a `<script>` whose content is escaped. Generated output is unchanged: the scaffold's `dist/index.html`, `dist/about.html` and `dist/style.css` are byte-identical across this change, since the existing CSS avoided the affected characters by construction.
- **`Handler` carries either a Caja function or JavaScript** — a new `script` field, with exactly one of the two meaningful. `renderToString` emits the JavaScript as an inline event attribute (`onclick='...'`, which needs no escaping change: a browser entity-decodes an attribute value before interpreting it as JavaScript) and now warns only about handlers it genuinely cannot honour, rather than about every handler on the View. `@caja/dom`'s `mount()` keeps attaching `.handler` and ignores script-only handlers, so a web-app build is unaffected.
- **Builtin `String` parameters accept a `Script`** — the ~20 hand-written `!= STRING_OBJ && != ANY_OBJ` checks in `analyzer/builtin.go` are replaced by one `acceptsStringArg` predicate. Without this, `Script` widened to `String` for ordinary Caja functions and struct fields (via `BasicSymbol.Equals`) but not for builtin module calls, so `string.len`, `string.contains` and `doc.write` rejected it — an arbitrary hole in a type that behaves like a string everywhere else. Writing a validated `Script` straight to a `.js` file with `doc.write` now works.
- **Breaking: `@caja/ui`'s `el()` is now `view()`, and every `View`-typed parameter is named `target`** — the constructor returns a `View`, so that is what it is called. The parameter rename is the consequence: ~70 functions took a parameter named `view`, which would now silently shadow the constructor. That shadowing is merely harmless today rather than broken (the cross-module resolution bug in `transpiler.go`'s `resolveIdentifierGoName` is fixed), but a modifier that later needed to build a `View` of its own would fail confusingly, and this library already avoids this class of collision deliberately elsewhere (`elementId` not `id`, `mainEl` not `main`). The same hazard reaches consumer code through a wildcard import: the web-app scaffold's root local is now `root`, not `view`. No caller used named arguments for any renamed parameter.
- **Breaking: `stylesheet` takes keyframes first** — `stylesheet(frames, rules, classes, queries)`. The parameter order is the emit order and the emit order is the cascade order: `@keyframes` first (at-rules, referenced by name and unaffected by the cascade), then rules, then classes, then media queries.
- **Breaking: `Page`/`definePage` live only in `@caja/ui`** — siriguela declared a second, identical `Page` struct and `definePage`, so the two packages disagreed about a type whose identity is nominal. A page with a title, an output path and some content — and a nav link that knows which page is current — are universal, with nothing theme-specific to decide. siriguela keeps only the part that IS a theme decision: `siteNav` (now `navLinks` plus a class), `renderPage` and `siteStylesheet`, all typed on ui's `Page`.
- **The static-page and web-app scaffolds import `@caja/ui` directly** — `import * from "@caja/siriguela"` *and* `import * from "@caja/ui"`, in every template file. This relaxes the earlier "templates may use only siriguela names" rule, which had forced a theme component to be invented for every structural need; reach for a themed component first and drop to ui for anything structural. Verified disjoint: 280 ui exports vs 42 siriguela exports, zero overlap, so wildcard-importing both is collision-free. The `as ui` alias the templates carried (which aliased *siriguela*) was dropped as actively misleading now that `@caja/ui` is a direct import too.
- **@caja/ui emits no hand-written CSS strings any more** — `skeletonStyles`, `spinnerStyles`, `tooltipStyles` and the three `tabStyleRules` helpers built their CSS by string concatenation, predating the `Rule`/`Class`/`MediaQuery` APIs that can express it. They are now `pulseKeyframes()`/`spinKeyframes()` (`-> Keyframes`), `tooltipRules()` and `tabRules(groupName, items)` (`-> [Rule]`), with the old `<style>`-View entry points kept as thin wrappers. Each is exposed both ways on purpose: prefer the Caja value and fold it into your own `stylesheet()` call, so the rules ship once in the `.css` file with none of the `<`/`>`/`&` escaping constraint a `<style>` View's text carries. Generated output is unchanged apart from `renderStyleDeclarations` terminating each declaration with `;` (`{display:none}` → `{display:none;}`); `dist/style.css` and `dist/about.html` are byte-identical across the change, and `dist/index.html` differs only by those semicolons in the two generated tab `<style>` blocks.
- **`ui/index.caja` is reordered into nine numbered sections** — enums, core types, primitives, modifier chain, events, rendering, CSS-in-Caja, component catalog, site model. Not only tidiness: Caja has no forward references between separate bindings, so the reading order *is* the dependency order, and the composite components (`tabs`, `tooltip`, `skeleton`, `spinner`) had to move below the CSS section to be able to build a `Rule` at all.
- **Breaking: the structural packages are `@caja/ui` and `@caja/dom`** — what started as `siriguela`'s internals became `@caja/core-ui` when the theme was split out, and is now simply `@caja/ui` (folder `ui/`); the DOM renderer went `@caja/siriguela-dom` → `@caja/core-ui-dom` → `@caja/dom` (folder `dom/`). The renderer never had anything to do with the siriguela theme — it only ever walks the four structural types — so its original name implied a dependency that no longer exists. The two `@keyframes` identifiers `@caja/ui` emits are now `caja-ui-pulse`/`caja-ui-spin`; they are private, referenced only by the rule that defines them.
- **siriguela reaches `@caja/ui` only through a qualified import** — values *and* types (`ui.column(...)`, `x: ui.View`, `-> [ui.Rule]`), with nothing imported by name. Since a named import is forwarded to the importing module's own consumers but a qualified one is not, "siriguela re-exports nothing" is now true by construction rather than by discipline. This corrects an earlier assumption in this branch that a type had to be imported by name because it could not be written qualified — qualified type annotations work fine, including array forms; the test that suggested otherwise was failing on an unrelated parse error in the same file.
- **Breaking: siriguela no longer re-exports ui; it owns its components** — the theme used to forward ui's ~170-name catalog through a named-import facade, so a consumer's code silently depended on which names happened to be forwarded. It now exports **only its own declarations**: the palette and themed components (`primaryButton`, `card`, `themedAlert`, `heroPanel`, ...), a prose-and-layout vocabulary (`stack`, `pageContent`, `paragraph`, `codeSample`, `bulletList`, ...), the documentation units a reference page is written in (`docSection`, `componentDoc`, `masthead`, `tocNav`, `paletteTable`, `docTabs`), and its own `Page` type with `definePage`/`siteNav`/`renderPage`/`siteStylesheet`. Consumers write siriguela and never see a ui name. The static-page scaffold follows suit: `main.caja` is now ~45 lines (a page list, a footer note, a recursive writer) because the shared chrome moved into `renderPage` and the whole stylesheet into `siteStylesheet`, and the doc page documents siriguela's own API rather than enumerating ui's catalog. Building a theme of your own means importing ui directly, which is what that package's README is for.
- **Breaking: the UI library is split into `@caja/ui` and `@caja/siriguela`** — `ui/` is a new package holding everything that generates HTML and CSS with no opinion about appearance (the `View` tree and its types, `el`/`attr`/`style`, the modifier chain, the structural component catalog, `renderToString`, `Page`/`definePage`/`navLinks`/`htmlDocument`, and the `Class`/`Rule`/`MediaQuery` CSS-in-Caja APIs). `siriguela/` keeps only the theme: the palette, `primaryButton`/`secondaryButton`/`card`/`pageHeading`/`themedLink`, and the `Variant` enum with `themedAlert`/`themedBadge`. Consumers still write **one** import — siriguela — and a project that wants a different look builds on ui directly instead of stripping out a palette it never wanted (see the entry above for how siriguela exposes its surface). `@caja/dom` now depends on ui rather than on the theme, which is the correct direction — `mount()` only ever walks the four structural types, and a `View` is the same nominal type whichever package a consumer reached it through. Both packages must be linked into `node_modules/@caja/` until they are published. The two `@keyframes` names ui emits were renamed `siriguela-pulse`/`siriguela-spin` → `caja-ui-pulse`/`caja-ui-spin`; they are private identifiers referenced only by the rule that defines them, so generated pages are otherwise byte-identical.
- **Breaking: the `page` builtin module is now `doc`** — `import doc` / `doc.write(path, content)`. No compatibility alias: `import page` fails to resolve. The name says what the one function does (write a document) and frees "page" for what it now means in siriguela — a page of a site (`Page`, `definePage`). Internals renamed to match (`UsesDocModule`, `caja_doc_write`); `caja run`'s refusal message says "doc module".
- **siriguela: `renderStyleDeclarations` no longer attribute-escapes each value** — escaping now happens once over the joined declaration list where the `style='...'` attribute is assembled, so the inline-style output is byte-identical, but the raw `prop:val;` joiner can also feed a real stylesheet (`classCss`) where a `'` in `font-family:'Inter'` must stay a `'`, not become `&#39;`. Anyone hand-building `.css` from `Style` arrays gets un-mangled quotes now.

### Fixed
- **The compiler package's HTTP tests bound hardcoded ports** — each of the nine `http*` samples had its port written twice, once in the `.caja` source and once as a matching test constant, and nothing reserved it. Any overlapping `go test` run, a server left behind by a killed run, or an unrelated process on the same port produced `bind: address already in use` / `connection reset by peer` on a different, arbitrary subset of tests each time — a failure that looks like a logic bug and is not one. The tests now reserve a free port from the OS and start the sample on it through `CAJA_HTTP_PORT`, the same override `caja listen --port` uses and the same approach `cmd/cli`'s `build_test.go`/`serve_test.go` already took; the samples keep their readable hardcoded ports. Verified by running two concurrent copies of the suite: previously a coin-flip, now every dynamic-port test passes in both. One address stays fixed by design — `samples/http_client` hardcodes the URL its Client calls (`http://127.0.0.1:8102`) in its own source, and `CAJA_HTTP_PORT` only overrides `http.listen`, not an outbound client URL — so two overlapping runs still collide on that single test pair, which is documented where the constant lives.
- **`and`, `or` and `xor` never compiled** — Caja's three boolean keyword operators reached Go as the bare keyword (`var ok bool = (a and b)`), which no Go compiler will parse. Every earlier stage was fine: the lexer had the tokens, the parser built the node, and the analyzer type-checked all three as two Booleans — so nothing objected until the final `go build`, which failed with a syntax error pointing at Go source the user never wrote. `transpileExpression`'s `*ast.InfixExpression` case already special-cased `%` and `^` (which Go spells differently) and simply never got the same treatment for these: `and` now lowers to `&&`, `or` to `||`, and `xor` to `!=` — inequality *is* exclusive-or for two booleans, whereas Go's `^` is bitwise and only defined on integers. `&&`/`||` short-circuit, which is the conventional reading and is now covered by a test, alongside the full 12-case truth table run as real programs (asserting on emitted text would have passed against the broken output too). `@caja/js` was written around the gap with nested guards; those are back to a single `or`.
- **The static-page scaffold wrote no HTML at all**: `main.caja.tmpl` had lost its final `writeSite(site, site)` call to a stray `let rules = [baseRules()]` line, which additionally referenced a `private` siriguela function and so failed analysis outright. Restored the call; the scaffold builds and populates `dist/` again.
- **`@caja/siriguela`'s `onClick`/`onInput` recursed forever**: both were written as `const onClick = fn(view: View, handler) { return onClick(view, handler) }`, intended to delegate to `@caja/ui`'s. But siriguela reaches ui through `import * from "@caja/ui"`, and a wildcard-imported name is *silently* shadowed by a same-named local declaration — so each wrapper called itself. It compiled and type-checked cleanly; only running it would have overflowed the stack. Both are deleted rather than repaired: a theme has no opinion about an event, so the whole handler surface belongs to ui. The general rule this exposed — the two packages' export surfaces must stay disjoint, since a wildcard import gives no "already declared" error to catch the overlap — is now documented in both packages and verified mechanically.
- **Non-tail-call self-recursion failed to compile**: a `let`/`const`-bound function whose recursive call wasn't a pure tail call (e.g. classic `return n * fact(n - 1)`, or the function passing its own name along as a value) transpiled to a single Go `var f T = func(...){ ...f... }` statement, which Go rejects (`undefined: f`) since a variable's own initializer can't reference it — even inside a closure literal that isn't actually invoked until later. The analyzer always accepted this as valid recursion; only the real `go build` path was affected, which is why it went unnoticed. Fixed by splitting into a declare-then-assign pair (`var f T; f = func(...){...}`) whenever a function literal's body references its own bound name — the standard Go idiom for self-referencing closures.
- **`caja build` could pick the wrong compile target for a declared project**: once a project declares its type via `cajaproj.yml`, `build.go` was still ORing that against `compiler.UsesBrowserModule` sniffing the transpiled Go source for a `syscall/js` import, rather than letting the declared type decide outright. A `static-page` (or `http-api`) project whose code merely *referenced* `browser.*` anywhere — even inside an imported library function nothing in the program ever called — got compiled to `wasm` and then crashed with `exec format error` when the static-page build path tried to run that wasm binary as a native generator. Fixed: with a declared project type, only that type decides the target (`web-app` → `js`/`wasm`, everything else → native); the `UsesBrowserModule` heuristic is now only consulted as a fallback for a standalone script with no `cajaproj.yml` at all.
- **A function parameter shadowing an unrelated sibling global resolved to the wrong binding, but only across a cross-module import**: `transpiler.go`'s identifier-resolution only checked whether a global with the *same name* existed anywhere in the module and whether this identifier's own definition lived in that module's file — both trivially true for a local parameter/`let` sharing a name with an unrelated top-level binding too, since it's declared in that same file. A parameter shadowing a same-named global elsewhere in its own module got module-prefixed and resolved to the *global* instead, real miscompilation (silent wrong-value substitution whenever the two happened to share a type, a genuine type error otherwise). Fixed by additionally requiring this occurrence's own resolved definition token to match the global scope entry's — confirming it actually refers to the global, not merely shares its name.
- **Re-exporting a named-imported `enum` emitted a reference to a Go symbol that never existed**: a facade module that named-imports an enum purely to forward it (`import { CSSProperty } from "@caja/ui"`) made `writeReexportForwards` emit `var facade_CSSProperty T = origin_CSSProperty` — but an enum has no Go declaration of its own (it emits nothing; a member access inlines the member's literal), so the generated program failed to build with `undefined: origin_CSSProperty`. Any module in the chain that merely *mentioned* the enum's name was enough to trigger it. Fixed by skipping enums when emitting re-export forwards: both of an enum's uses — as a type annotation, resolved through the symbol table, and as `E.Member`, inlined at the use site — work without a runtime value to forward. This is what the `@caja/siriguela` → `@caja/ui` facade depends on.
- **`import { Name } from "mod"` couldn't resolve an `enum`**: named-import resolution tried a value lookup first and only fell back to a type lookup if that failed — but an `enum`'s name is deliberately registered as *both* a value (so `Enum.Member` resolves) and a type (so `x: Enum` resolves), so the value lookup always succeeded first and the type registration was never reached. `import { CSSProperty } from "@caja/siriguela"` (or any named-imported enum) now resolves both forms, matching what `import * from "mod"` already did correctly (its two independent loops don't have this if/else-if ordering problem). Fixed by checking both forms independently rather than as a chain — restoring the pre-existing private-member rejection along the way, since `GetType` doesn't filter private types itself and the ordering change had to keep that check.

## [v0.1.0-alpha.5] - 2026-08-29

### Added
- **VS Code Extension**: Introduced the official Caja VS Code extension with foundational syntax highlighting (PR #73).
- **Language Server Protocol (LSP)**: Implemented full LSP support inside the Caja CLI to bring advanced IDE features to the editor (PR #74).
  - **Live Diagnostics**: Real-time syntax and semantic error highlighting as you type.
  - **Hover Information**: Instantly view inferred types, struct layouts, and function signatures.
  - **Go to Definition (Cmd+Click)**: Navigate directly to variable, function, and struct definitions, including cross-file module navigation.
  - **Signature Help**: Display parameter hints and active parameter tracking while typing function calls.

### Performance & Architecture Optimizations
- **Single Worker Pattern**: The LSP safely processes requests sequentially per document, completely eliminating CPU spikes caused by overlapping parses on rapid keystrokes.
- **Early Context Cancellation**: Intermediate keystrokes instantly cancel mid-flight background validations, freeing up CPU resources for the most recent AST changes.
- **Lock-Free Fast Reads**: ASTs and Analyzers are safely cached using `sync.RWMutex`, allowing LSP operations like Hover and Go To Definition to read from memory in `O(1)` time without triggering expensive re-parses.

### Fixed
- **Parser Crash Fix**: Fixed a critical interface typed-nil bug in the parser that caused panics when evaluating incomplete statements (e.g., `let`, `const`, `return`, `import`, `type`).
- **Syntax Enforcement**: The parser now strictly enforces newlines between statements.

### Documentation
- Created this comprehensive human-readable root `CHANGELOG.md` to document all notable changes across alpha releases.
- Standardized the VS Code extension's `CHANGELOG.md` to adhere to the "Keep a Changelog" format.

## [v0.1.0-alpha.1] - 2026-08-18

This was the monumental initial release of the Caja Language, laying down the fundamental compilation pipeline, language features, and standard library.

### Core Architecture
- **Pipeline Implementation**: Built the core Lexer/Tokenizer, Pratt Parser, Semantic Analyzer, and Tree-Walking Evaluator (PR #2, #4, #5, #12).
- **Refactoring & Scoping**: Refactored the compiler into an encoder and introduced block scoping (PR #13, #14).
- **NPM Integration**: Configured initial GitHub Actions for deploying the `cajac` CLI to npm (PR #1, #55).

### Language Features
- **Data Types & Structures**: Implemented Primitives, Arrays, Native Dictionary Maps, Structs, and Date types (PR #17, #22, #40, #44).
- **Advanced Typing**: Introduced Generics (for functions, structs, and aliases), Nullable Types, and a `Nothing` type for implicit returns. Enforced generic constraints and removed the permissive `Any` type (PR #40, #47, #50, #53).
- **Immutability & Purity**: Enforced deep immutability and function purity inside the semantic analyzer (PR #54).
- **Functions & Flow**: Added support for Higher-order functions, Inline arrow functions, Recursive functions with Tail Call Optimization, and declarative `if-else` expressions (PR #11, #15, #18, #19, #20, #48).
- **Variable Modifiers**: Introduced `let`, `const`, and `private` access modifiers (PR #13, #37, #38).
- **Operators**: Implemented the data-first pipe operator (`|>`), boolean logic (`and`, `or`, `xor`), prefix operators, exponential (`^`), and modulo (`%`) (PR #9, #10, #28, #29, #33, #52).

### Standard Library (Built-ins)
- **Math**: Added the `math` module with constants (like `PI`), functions, and `math.rand()` (PR #31, #35, #43).
- **Strings & Dates**: Added robust string manipulation and date processing functions (PR #26, #27).
- **Casting**: Implemented the `cast` module for safe type conversions (PR #46).
- **Collections**: Added polymorphic array functions and `map.delete` for dictionaries (PR #24, #49).
- **Logging**: Added the `log` module for console outputs (PR #36).
- Migrated many built-in modules to use the new Generics system (PR #51).
