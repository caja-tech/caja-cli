# cmd/cli

## Purpose

The `caja` binary's entrypoint — a Cobra-based CLI that composes every other package in the repo into the commands end users actually run (`init`, `run`, `build`, `serve`, `listen`, `encode`, `decode`, `lsp`). This is the composition root: nothing in the repo depends on it, it depends on almost everything.

## Integration

- **Imports:** `internal/file`, `internal/project`, `internal/script`, `internal/lsp`, `internal/encoder`, `internal/pipeline/compiler`, `internal/pipeline/environment`.
- **Depended on by:** nothing — this is the leaf/executable package.

## How it works

- `main.go` wires every `New*Cmd()` constructor into the root command and calls `root.Execute()`. Holds the `Version` var, overridden via `-ldflags` at release build time, and passed through to `lsp.Run` and stamped into a scaffolded project's `cajaproj.yml` by `init.go`.
- `root.go`: `NewRootCmd()` — base `caja` command; shows help when run with no subcommand.
- `init.go`: `NewInitCmd()` — scaffolds a new project (`cajaproj.yml` + `main.caja` + `README.md`, plus a `.gitignore` for static-page) from the per-type templates embedded via `templates.go`'s `//go:embed all:templates`, rendered with `text/template` against `{Name string}`. Refuses to scaffold into a non-empty directory (no `--force` yet). `renderProjectTemplates` creates nested template directories as it walks (`os.MkdirAll` on the directory entries) — before the static-page `pages/`/`assets/` subfolders existed every template dir was flat, and a nested `.tmpl` would have failed with "no such file or directory" because `os.Create` doesn't make parents. go:embed can't carry an empty directory, so a scaffolded folder always ships at least one real file (`assets/siriguela.svg`).
- `project.go`: not a command — `resolveProjectContext(filePath string) (string, *project.Manifest, error)` is the shared auto-discovery helper `run`/`build`/`serve`/`listen` all call first. An explicit `--file` always wins outright, bypassing manifest lookup entirely (byte-identical behavior to a standalone script with no `cajaproj.yml` around); only when `--file` is empty does it look for `cajaproj.yml` in the cwd via `internal/project.Load` and resolve to its declared entry file. Also holds the static-page generation helpers: `generateStaticPage` (the single path both `build` and `serve` call — `runBuiltBinaryOnce` then `RemoveAll(dist/assets)` + `copyDir(assets → dist/assets)`, skipped when the project has no `assets/`) and the `filepath.WalkDir`-based `copyDir`. Keep the two commands on that one helper; they used to inline the orchestration separately, which is exactly how an assets step added to one would have missed the other.
- `run.go`: `NewRunCmd()` — reads a `.caja` file (via `resolveProjectContext`), calls `script.ParseWithDir` then `script.Run`, prints the result via `environment.PrintObject`. Refuses browser-module and doc-module scripts (`compiler.UsesBrowserModule`/`UsesDocModule`) with a message pointing at `caja build` instead — both would otherwise "succeed" in a broken way (`go run` can't build `GOOS=js`; a doc-module script's `doc.write` output would land in the throwaway temp dir `compiler.Run` deletes on exit). The doc module was named `page` until the static-page multi-page work; the rename is deliberate and has no compatibility alias — "doc" says what `write` does, and "page" now means a page of a site (siriguela's `Page`). The `--export`/`-e` flag reads `globalEnv.ExportedValues` and writes them to CSV, special-casing `*environment.Array` values (flattened into CSV columns) versus scalar values (written as a single column) — a Caja-specific convention, not a generic CSV writer.
- `build.go`: `NewBuildCmd()` — `script.ParseWithDir` → `compiler.Transpile` → `go/format.Source` → `compiler.Compile`, which triggers `toolchain.EnsureToolchain()` internally. `--emit-go` dumps the intermediate transpiled Go source instead of (or alongside) building. Project-type-aware once a manifest resolves the file: a declared `web-app` targets `GOOS=js/GOARCH=wasm` even before `UsesBrowserModule` would infer it, and also mirrors the browser harness as `index.html` so the output directory is servable at a domain root by any static host with no config; a declared `static-page` goes through `generateStaticPage` (project.go): run the freshly-built binary once so its `doc.write` calls populate `dist/`, then mirror `assets/` into `dist/assets/` (recreated from scratch each time; a project with no `assets/` is left untouched); `http-api` gets no special branch at all — it's just a native binary like any other script, since the `http` builtin module needs no compiler-side special-casing to build.
- `serve.go`: `NewServeCmd()` — project-type-aware dev server. `buildBrowserPageServer` (web-app / any standalone browser-module script) force-builds `GOOS=js/GOARCH=wasm` and serves the harness directory; `buildStaticPageServer` (static-page) builds natively, runs the binary once, and serves `dist/`; a declared `http-api` is refused with a message pointing at `caja listen` instead — there is no "serve" concept for a live backend process.
- `listen.go`: `NewListenCmd()` — runs an http-api script live via `compiler.Run` (transpile + `go run`, not a saved binary), auto-discovering `main.caja` through `resolveProjectContext` the same way the other commands do. `--port` is threaded through as the `CAJA_HTTP_PORT` env var, which the generated `caja_http_listen` call (compiler/builtins.go) prefers over the port literal baked into the `.caja` source — so the invocation, not the script, controls the actual bind port.
- `encode.go` / `decode.go`: thin wrappers around `internal/encoder.Encode`/`Decode`.
- `lsp.go`: `NewLspCmd()` — calls `lsp.Run(Version)`.
- `templates.go` + `templates/{static-page,web-app,http-api}/`: the `caja init` scaffold content, one `*.tmpl` file per output file (`.tmpl` stripped on render). Caja string literals now support real backslash escapes (`\"`, `\n`, `\t`, `\\`, `\'`, `\$`, `\uXXXX`) — the web-app/http-api templates predate that and still use `'` for nested HTML-attribute quoting rather than `\"`, which is harmless (HTML accepts either) but no longer required; don't assume `\"` is unavailable if you're touching a template.
  - Two escaping traps specific to these files, both of which the static-page template hits. First, they are rendered by `text/template`, so a literal `{{` anywhere in the file is parsed as an action — keep a newline or space after every `{` in embedded CSS/Caja samples. Second, Caja now interpolates `${...}` inside string literals, so a code sample that *shows* interpolation has to write `\${...}` or it gets evaluated at build time instead of displayed.
  - `templates/static-page/` is not a minimal stub — it scaffolds a small multi-page site: `main.caja.tmpl` is the site builder (page list, shared layout with `navLinks`, a recursive `writeSite` loop, and the entire stylesheet built in Caja via `ui.Rule`/`ui.media`/`ui.stylesheet` — no hand-written CSS string anywhere in the template); `pages/index.caja.tmpl` is a complete, self-documenting siriguela reference (every component's signature, a sample, and the live rendering of that sample, built using only siriguela); `pages/about.caja.tmpl` is a second page that exercises `assets/` (an `<img>` of `assets/siriguela.svg`) and a Caja-defined `Class`. Together they are the de-facto integration test for `@caja/siriguela` — a catalog change that breaks a component shows up in `caja init --type static-page` + `caja build` immediately, and the build is also the only place the three-module `Page` round-trip (defined in siriguela, instantiated in a page module, consumed in `main.caja`) is exercised. Page modules never `import doc`; only `main.caja` writes. The stylesheet deliberately uses child combinators (`.tabs > input`) to scope the tabs/toggle rules: the demos inside a tab panel include radios and checkboxes of their own, which a descendant selector would hide. `main.caja.tmpl` builds three `[ui.Rule]`/`[ui.MediaQuery]` lists and one `[ui.Class]` list, joins the rule lists with `array.join` (no varargs/spread), and calls `ui.stylesheet(rules, classes, queries)` once for the whole file — a `Rule`'s selector is a raw string with no compile-time validation (only its declarations go through `CSSProperty`), so a typo'd selector fails silently at the CSS level, not the Caja level.

## Gotchas / invariants

- The `.caja`-extension validation (`filepath.Ext(filePath) == file.EXTENSION`) is duplicated across `run.go`, `build.go`, `listen.go`, and `encode.go` rather than centralized in one helper. This is a known repetition, not an oversight to silently "fix" as a side effect of an unrelated change — if you do centralize it, update all four call sites deliberately.
- `run.go`'s CSV export logic is the one place in the CLI layer that has Caja-value-shape-aware behavior (array-flattening) baked directly into command code rather than pipeline code — worth knowing before assuming all `environment.Object` formatting lives in `internal/pipeline/environment`.
- `resolveProjectContext` is only ever consulted when `--file` is empty — a `cajaproj.yml` sitting in the cwd has zero effect on a command invoked with an explicit `--file`. Don't assume manifest-declared type ever overrides an explicit `--file` invocation; it doesn't, by design (see [[../internal/project/CLAUDE.md]]).
- `caja build` has no http-api branch because none is needed today — if the `http` builtin module ever needs a build-time step analogous to static-page's generator-run or web-app's harness, that's exactly where it would go, following the same `manifest.Type == project.TypeX` pattern the other two branches use.
