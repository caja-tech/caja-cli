# cmd/cli

## Purpose

The `caja` binary's entrypoint — a Cobra-based CLI that composes every other package in the repo into the commands end users actually run (`init`, `run`, `build`, `serve`, `listen`, `encode`, `decode`, `lsp`). This is the composition root: nothing in the repo depends on it, it depends on almost everything.

## Integration

- **Imports:** `internal/file`, `internal/project`, `internal/script`, `internal/lsp`, `internal/encoder`, `internal/pipeline/compiler`, `internal/pipeline/environment`.
- **Depended on by:** nothing — this is the leaf/executable package.

## How it works

- `main.go` wires every `New*Cmd()` constructor into the root command and calls `root.Execute()`. Holds the `Version` var, overridden via `-ldflags` at release build time, and passed through to `lsp.Run` and stamped into a scaffolded project's `cajaproj.yml` by `init.go`.
- `root.go`: `NewRootCmd()` — base `caja` command; shows help when run with no subcommand.
- `init.go`: `NewInitCmd()` — scaffolds a new project (`cajaproj.yml` + `main.caja` + `README.md`, plus a `.gitignore` for web-app) from the per-type templates embedded via `templates.go`'s `//go:embed all:templates`, rendered with `text/template` against `{Name string}`. Refuses to scaffold into a non-empty directory (no `--force` yet). The npm install step is gated on `scaffoldHasPackageJSON(targetDir)` — whether the rendered scaffold actually contains a `package.json` — not on a hardcoded list of project types: adding dependencies to a project type is then purely a matter of adding a `package.json.tmpl` to its template tree. Both project types ship one: web-app (`@caja/siriguela`, `@caja/ui`, `@caja/js`) and http-api (`@caja/acerola`). `installDependencies` degrades a failed install to a warning, which matters right now because none of the `@caja/*` UI packages are published, so a real `caja init --type web-app` prints that warning every time until they are — the only thing keeping that from being a fatal `init` failure. `renderProjectTemplates` creates nested template directories as it walks (`os.MkdirAll` on the directory entries) — before the web-app template's `pages/`/`assets/` subfolders existed every template dir was flat, and a nested `.tmpl` would have failed with "no such file or directory" because `os.Create` doesn't make parents. go:embed can't carry an empty directory, so a scaffolded folder always ships at least one real file (`assets/siriguela.svg`).
- `project.go`: not a command — `resolveProjectContext(filePath string) (string, *project.Manifest, error)` is the shared auto-discovery helper `run`/`build`/`serve`/`listen` all call first. An explicit `--file` always wins outright, bypassing manifest lookup entirely (byte-identical behavior to a standalone script with no `cajaproj.yml` around); only when `--file` is empty does it look for `cajaproj.yml` in the cwd via `internal/project.Load` and resolve to its declared entry file. Also holds the web-app generation helpers: `generateWebApp` (the single path both `build` and `serve` call — `runBuiltBinaryOnce` then `RemoveAll(dist/assets)` + `copyDir(assets → dist/assets)`, skipped when the project has no `assets/`) and the `filepath.WalkDir`-based `copyDir`. Keep the two commands on that one helper; they used to inline the orchestration separately, which is exactly how an assets step added to one would have missed the other.
- `run.go`: `NewRunCmd()` — reads a `.caja` file (via `resolveProjectContext`), calls `script.ParseWithDir` then `script.Run`, prints the result via `environment.PrintObject`. Refuses doc-module scripts (`compiler.UsesDocModule`) with a message pointing at `caja build` instead — a doc-module script's `doc.write` output would otherwise land in the throwaway temp dir `compiler.Run` deletes on exit. The doc module was named `page` until the multi-page work; the rename is deliberate and has no compatibility alias — "doc" says what `write` does, and "page" now means a page of a site (siriguela's `Page`). The `--export`/`-e` flag reads `globalEnv.ExportedValues` and writes them to CSV, special-casing `*environment.Array` values (flattened into CSV columns) versus scalar values (written as a single column) — a Caja-specific convention, not a generic CSV writer.
- `build.go`: `NewBuildCmd()` — `script.ParseWithDir` → `compiler.Transpile` → `go/format.Source` → `compiler.Compile`, which triggers `toolchain.EnsureToolchain()` internally. `--emit-go` dumps the intermediate transpiled Go source. Every project compiles to a **native** binary; `--os`/`--arch` are the only target overrides, and there is no browser/wasm branch any more. A declared `web-app` then goes through `generateWebApp` (project.go): run the freshly-built binary once so its `doc.write` calls populate `dist/`, then mirror `assets/` into `dist/assets/` (recreated from scratch each time). `http-api` gets no special branch — it is just a native binary.
- `serve.go`: `NewServeCmd()` — builds the project and serves its generated `dist/` over HTTP. One serving path now: a declared `http-api` is refused with a message pointing at `caja listen`, and everything else (a `web-app`, or a standalone script with no manifest) goes through `buildWebAppServer`. Its `init()` registers `application/manifest+json` for `.webmanifest`, which Go's mime table lacks — a manifest served as `text/plain` makes Chrome warn and Lighthouse mark the app uninstallable. Serving over HTTP rather than `file://` is not a convenience: a service worker will not register under `file://`.
- `listen.go`: `NewListenCmd()` — runs an http-api script live via `compiler.Run` (transpile + `go run`, not a saved binary), auto-discovering `main.caja` through `resolveProjectContext` the same way the other commands do. `--port` is threaded through as the `CAJA_HTTP_PORT` env var, which the generated `caja_http_listen` call (compiler/builtins.go) prefers over the port literal baked into the `.caja` source — so the invocation, not the script, controls the actual bind port.
- `encode.go` / `decode.go`: thin wrappers around `internal/encoder.Encode`/`Decode`.
- `lsp.go`: `NewLspCmd()` — calls `lsp.Run(Version)`.
- `templates.go` + `templates/{web-app,http-api}/`: the `caja init` scaffold content, one `*.tmpl` file per output file (`.tmpl` stripped on render). Caja string literals now support real backslash escapes (`\"`, `\n`, `\t`, `\\`, `\'`, `\$`, `\uXXXX`) — the web-app/http-api templates predate that and still use `'` for nested HTML-attribute quoting rather than `\"`, which is harmless (HTML accepts either) but no longer required; don't assume `\"` is unavailable if you're touching a template.
  - Two escaping traps specific to these files, both of which the web-app template hits. First, they are rendered by `text/template`, so a literal `{{` anywhere in the file is parsed as an action — keep a newline or space after every `{` in embedded CSS/Caja samples. Second, Caja now interpolates `${...}` inside string literals, so a code sample that *shows* interpolation has to write `\${...}` or it gets evaluated at build time instead of displayed.
  - **JavaScript in a generated page** is built as a tree by `@caja/js` and rendered by it: `@caja/ui`'s `onX` handlers and `scriptBlock` take a `[JsStmt]`, so `ui` depends on `@caja/js`. Correctness comes from construction — expressions and statements are separate types, and `jsStr` escapes its input — rather than from parsing the result. `@caja/ui` owns the ~90 `onX` event handlers; each takes a `[JsStmt]` and is emitted as an inline event attribute, which the browser runs. There is only one kind of handler — a generated page has no Caja runtime, so a Caja function could not be called from an event even in principle. The `js` **builtin** module is the complement for hand-written JavaScript: `js.raw("...")` returns an opaque `Script`, and `jsRaw`/`jsRawStmt` are the only nodes that accept one, which keeps the single door for arbitrary syntax a door that validates. A consumer can hand-build a node (struct literals are public) but not one carrying arbitrary text — `field 'script' expects Script, got String`. `js.raw`'s argument must be a string *literal*, because the analyzer parses it with esbuild at compile time (`internal/pipeline/analyzer/javascript.go`) — validation has to run inside the caja binary, since `compiler.Compile` builds the generated program as a stdlib-only module (`go mod init caja_build`, `CGO_ENABLED=0`, no dependency resolution) and so emitted code could never import a JS parser. A `Script` erases to a Go `string` and registers no `usedModules` entry. `Script` widens to `String` one-directionally (like an enum to its backing type — `BasicSymbol.Equals`, plus `acceptsStringArg` for builtin parameters), so a `String` never narrows back and every script is forced through the validator.
  - `templates/web-app/` is not a minimal stub — it scaffolds a small multi-page site: `main.caja.tmpl` is the site builder (page list, footer note, a recursive `writeSite` loop, two `doc.write` calls, and nothing else — the shared chrome lives in siriguela's `renderPage` and the entire stylesheet in its `siteStylesheet`, so the scaffold has no hand-written HTML or CSS at all); `pages/index.caja.tmpl` is a complete, self-documenting siriguela reference (every component's signature, a sample, and the live rendering of that sample); `pages/about.caja.tmpl` is a second page that exercises `assets/` (an `<img>` of `assets/siriguela.svg`). Together they are the de-facto integration test for the UI packages — a catalog change that breaks a component shows up in `caja init --type web-app` + `caja build` immediately, and the build is also the only place the three-module `Page` round-trip (defined in `@caja/ui`, instantiated in a page module, consumed in `main.caja`) is exercised. Page modules never `import doc`; only `main.caja` writes. siriguela's stylesheet deliberately uses child combinators (`.tabs > input`) to scope the tabs/toggle rules: the demos inside a tab panel include radios and checkboxes of their own, which a descendant selector would hide. A `Rule`'s selector is a raw string with no compile-time validation (only its declarations go through `CSSProperty`), so a typo'd selector fails silently at the CSS level, not the Caja level.
  - Every template file imports **both** UI packages, each via `import * from "..."` (Caja's wildcard-import feature) with no alias, so their code reads as bare `card()`/`view(HTMLElement.Div)`/`View` rather than prefixed. The aliases these files used to carry (`as ui`, which aliased *siriguela*) were dropped as actively misleading once `@caja/ui` became a direct import too.
  - The UI library is **three** packages: `@caja/ui` (the View tree, the three enums, modifiers, the event-handler surface, the structural catalog, `renderToString`, the CSS-in-Caja APIs, and the `Page`/`definePage`/`navLinks`/`htmlDocument` site model — no palette, no opinion about appearance), `@caja/siriguela` (the default theme) and `@caja/js` (JavaScript as a Caja expression/statement tree, which `@caja/ui` renders into event attributes and `<script>` bodies). **siriguela does not re-export ui.** All 42 names it exports are its own declarations — the palette, themed components (`primaryButton`/`card`/`themedAlert`/`heroPanel`/...), a prose-and-layout vocabulary (`stack`/`paragraph`/`codeSample`/...), documentation units (`docSection`/`componentDoc`/`docTabs`/...), and the *themed chrome* around ui's site model (`siteNav`/`renderPage`/`siteStylesheet`). It reaches `@caja/ui` through `import * from "@caja/ui"`, and a wildcard import is deliberately NOT forwarded to the importing module's own consumers (only a named import is), so "re-exports nothing" holds by construction. A plain qualified import would forward nothing either; a **named** import is the only form that leaks.
  - The trap that comes with that wildcard, and it has already bitten once: a same-named local declaration *silently* shadows a wildcard-imported name, with none of the "already declared" error a named import gives. A `const onClick` in siriguela shadowed ui's and turned `return onClick(view, handler)` into infinite self-recursion. So **the two packages' export surfaces must stay disjoint** — currently 280 ui names vs 42 siriguela names with zero overlap, and worth re-checking mechanically after adding an export to either. The same hazard applies in consumer code: a local named `view` shadows ui's `View` constructor, which is why the web-app template's root local is called `root`.
  - Consequences worth keeping in mind before editing the templates: a template may use names from either package. Reach for a themed component first and drop to `@caja/ui` for anything structural — that is a deliberate relaxation of the earlier "templates see only siriguela" rule, which had forced a theme component to be invented for every structural need. A scaffolded project needs both packages linked into `node_modules/@caja/` until they're published; `package.json` declares them, but the install can only fail until publication.

## Gotchas / invariants

- The `.caja`-extension validation (`filepath.Ext(filePath) == file.EXTENSION`) is duplicated across `run.go`, `build.go`, `listen.go`, and `encode.go` rather than centralized in one helper. This is a known repetition, not an oversight to silently "fix" as a side effect of an unrelated change — if you do centralize it, update all four call sites deliberately.
- `run.go`'s CSV export logic is the one place in the CLI layer that has Caja-value-shape-aware behavior (array-flattening) baked directly into command code rather than pipeline code — worth knowing before assuming all `environment.Object` formatting lives in `internal/pipeline/environment`.
- `resolveProjectContext` is only ever consulted when `--file` is empty — a `cajaproj.yml` sitting in the cwd has zero effect on a command invoked with an explicit `--file`. Don't assume manifest-declared type ever overrides an explicit `--file` invocation; it doesn't, by design (see [[../internal/project/CLAUDE.md]]).
- `caja build` has no http-api branch because none is needed today — if the `http` builtin module ever needs a build-time step analogous to web-app's generator-run, that's exactly where it would go, following the same `manifest.Type == project.TypeX` pattern the other two branches use.
